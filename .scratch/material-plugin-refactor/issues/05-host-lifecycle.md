## Question

如何保证整体启动、能力登记事务、物料协作、冲突分级、异步迟到与宿主销毁拥有唯一可测试的语义？

## Answer

> 本票经逐轮讨论已收敛。以下记录已确认的生命周期语义及其代码落实约束，替代此前候选草案。翻译容错以用户后续修正为准；本票关闭不确认下游票据的字段、UI 或渲染会话细节。

承接唯一装配内核和完整物料使用方式。本票负责启动、回滚、诊断分级及销毁，不改变 Schema、节点工厂或既有正常编辑/渲染算法。

### 已确认：启动结果与销毁完成

承接[确定能力契约、宿主裁剪与包依赖方向](./04-contract-boundaries.md)：完整物料或集合一次传入，框架直接提供上下文，每实例唯一登记源，不要求应用另传宿主服务清单。用户对以下两项回复“两个都接受”，本节已确认；具体代码约束见后文。

1. 首版采用整体启动成功或整体失败：所选物料或扩展发生阻止核心能力正常工作的登记、初始化错误，或物料/插件身份冲突，则本次实例创建失败，撤销本次创建中已完成的登记并清理已取得的受管资源，不返回半可用实例。不在首版增加 optional 插件失败后跳过继续启动的模式。取舍是坏扩展会阻止该实例启动，但使用者无需配置必需/可选标志，也不会在启动成功后才发现部分所选功能悄悄缺失。翻译缺失、重复词条和可隔离的文本值问题不触发整体失败，按下方 locale 规则降级运行；不提供 optional 插件跳过模式不等于所有诊断都致命。这里仅指创建阶段；文档出现未安装的物料仍按既有未知物料规则处理，后续图片/数据加载、惰性 renderer 和命令执行失败不被自动等同为全实例安装失败。
2. 销毁可以等待完成：开始销毁立即停止接收新工作，使旧异步任务失去写回权限；框架尝试清理所有已取得的受管资源，一项清理报错仍继续其余项，完成结果汇总错误。重复销毁不重复释放。同一个实例的销毁不影响其他实例。无法取消、尚未返回的外部任务不无限阻塞销毁，但其迟到结果不能回写，若带来需释放的资源则由预先登记的处理器释放。

旧候选中的 optional 选择项、必需闭包升级、可选失败跳过已撤回。首版亦不预设 optionalDependencies 软排序与删环机制；如有真实需求再讨论，不能在实现中默认保留。具体 API 行为、清理顺序及错误结果见下文。

### 已确认：创建调用与重复登记

1. 程序化创建返回 Promise，成功时才交付可用实例；失败时先完成可等待的回滚，再拒绝 Promise，错误保留启动首因与清理错误。调用方使用 `await createViewer(...)` 和 `await viewer.destroy()`，不另需手动调用 install/start/ready。Vue Designer 组件由内部管理启动与卸载，使用者仍正常传入配置；组件的就绪/错误反馈形式在宿主迁移时细化，不在此假装已确定。登记同步提供完整声明，异步工作由框架调度，见下一节。
2. 重复身份明确报错、不按顺序覆盖：同一宿主重复插件身份或重复物料类型（包括重复传同一个物料）均视为配置错误；all 与 basic 重叠组合也应指出重复项。只有同一能力契约要求唯一的 key 才适用此规则，不把一种物料的 model、renderer、properties 视为彼此冲突。诊断包含冲突类型和双方来源。需要定制物料时创建前明确选择最终版本，具体便利接口留物料组合票据讨论，不强制用户操作内部 provider/plugin id。

确认来源：用户对以上两项回复“都接受”。这不提前决定 locale 词条冲突、多个 UI 扩展排序、具体错误类型或新公开函数的最终命名。

### 已确认：登记与异步加载的分工

物料/扩展在创建时同步提供完整的能力声明，框架统一收集、校验后封闭登记。作者不编写一个边 await 边补注册的安装过程，也不在登记时直接挂 UI、发起网络写入或创建无归属资源。内部若保留 setup，其职责仅为同步登记；这个内部步骤不成为普通物料作者额外必写的模板代码。

异步能力通过明确的 loader/factory 等回调声明，由框架在对应阶段调用并管理错误、取消和清理。启动必需的受管初始化由创建 Promise 等待，失败按已确认规则整体回滚；图表等按需加载的 renderer 在使用时加载，不因为创建变成 async 就在启动时下载全部惰性实现。节点数据、图片、字体等仍属于对应渲染任务，不作为登记时补装能力的手段。

因此“创建成功、所选能力就绪”表示完整声明通过校验且启动必需初始化完成，不保证未来每次网络请求或首次惰性加载一定成功。后续加载失败按运行阶段诊断处理，不回溯为启动失败；销毁后的迟到回调不得补注册或写回。

确认来源：用户对“物料一次声明完整能力，异步加载由框架负责调度”回复“接受”。具体 loader/factory 字段由物料与渲染会话票据落实，不要求作者手工声明安装顺序或服务清单。

### 启动流程与代码落实

`createHost(config): Promise<Host>` 是 runtime 内核入口；Designer / Viewer 的创建封装同样等待完成后返回可用 handle。流程为：

```text
validate complete material/extension configuration and host contracts
  -> synchronously collect all declarations into owned staging scopes
  -> validate core capability identities and final composition
  -> build per-host registry and non-blocking locale diagnostics
  -> await required managed consumer initialization
  -> return active Host
```

启动期间 registry 对外不可见，内部成功提交不代表消费者可以开始工作。同步登记、异步初始化由框架等待、创建返回 Promise 均已确认；内部若保留 setup 也仅同步登记。启动必需的核心消费者初始化失败清理整个 Host，不返回半可用对象；单个扩展 UI 的加载、挂载、渲染与回调失败按[UI 扩展的局部故障规则](./07-ui-slots.md#已确认扩展界面的局部故障)处理，不能因发生于首次显示就升级为核心初始化失败。active 后不能补装、移除或替换插件。

应用在创建前一次传入完整物料集合和独立扩展；宿主内部提供固定上下文和契约校验，不要求应用传宿主服务清单。创建后才 open / render / 编辑。文档引用未安装物料时遵循未知物料策略，与所选物料自身安装失败区分。物料完整性规则在物料票据收敛，不能通过缺失未知物料策略吞掉所选物料的配置错误。

### 已确认：物料协作与首版依赖范围

- 所有选择项均须成功，不提供 optional 跳过模式。
- 首版不公开 requires/optionalDependencies/before/after 等插件依赖或安装排序字段，不实现通用插件依赖解析器。完整物料的代码复用通过普通模块/包依赖解决；运行时协作通过框架已有受控上下文和能力消费者完成，不能直接取得另一个插件的可变实例。若某功能确实需要另一项能力，由该功能契约表达和校验，不让用户猜测 plugin id 或调整数组顺序。
- 框架先收集全部同步声明，再做组合校验，最后启动消费者；登记阶段不能读取“前一个插件已经初始化”的状态。这样运行时协作不依赖物料排列顺序。具体能力缺席是否可以降级由领域契约决定；例如未知节点和文案采用已确认降级，不能统称为硬依赖失败。
- 声明顺序保留为可复现的输入顺序，但不赋予它插件间初始化依赖语义。文案冲突选值仍按上节规则，UI 展示顺序在 UI 票据定义，与初始化顺序区分。
- 框架在开始消费前验证最终组合满足宿主核心契约，致命校验失败回滚所有已安装 Scope；这些规则不成为作者手填的 point/service 清单。
- setup 不能查询其他插件暂存贡献；需要协作的消费者在 active 后经受控只读服务取得最终能力快照。

取舍：首版支持完整物料和现有能力协作，但不支持第三方通过依赖字符串构建任意插件启动链。复杂协作可在同一个扩展内部组织，仍受统一资源所有权约束。确认来源：用户对“不增加 requires、before、after 等依赖与安装顺序配置”的推荐回复“接受”。

### 事务与冲突

以下落实已确认的整体回滚与实例隔离，不额外引入公共配置。owner 标识及事务状态由内核生成和维护，物料作者不用手写。UI 展示排序由 UI 票据规定。

每次安装产生独立 `installationId`；贡献 owner 为 `pluginId + installationId + contributionId`。同一 Host 重复 plugin id 直接配置失败，即使传入同一个对象也不自动去重。

注册先暂存；全部致命校验通过才提交，非阻断诊断随实例保留。核心能力登记错误把事务标为不可提交，即使 setup 捕获异常也不能恢复为成功；可恢复的文案诊断不使事务失败。启动失败清理失败项及此前本次启动中取得的全部受管资源；任何暂存登记都不作为可用实例对外交付。

| 场景 | 唯一结果 |
| --- | --- |
| 同一 Scope 重复 keyed key 或本地 contribution id | 本次事务失败；两次登记均不成为有效贡献，不保留“第一次注册” |
| 不同 Scope 在同一点争用唯一 key | 不覆盖，整体启动失败并清理本次创建的所有 Scope |
| 内部 setup 捕获核心注册异常后正常返回 | 事务仍失败，不能发布半个插件 |
| setup 抛错、返回 Promise | 当前事务失败并回滚；异步 setup 属于不受支持调用 |
| 任一所选插件发生致命安装错误或核心组合校验失败 | 整体回滚；创建 Promise 等待清理后拒绝，错误包含首因与所有清理错误 |
| 同一 key 的自定义 renderer | 创建前明确选择最终物料版本；具体定制接口由物料组合票据决定，不要求调用方拆内部能力 |
| UI list 展示顺序 | 由 UI 票据规定 order 与同序规则；不作为插件初始化依赖，文案使用自己的选值规则 |

keyed 冲突诊断包括 point、key、双方 owner；list 的完整 contribution id 在 Host 内唯一。registry 只能由 runtime 写入，宿主读取只读视图。

### locale 的确定规则

用户明确撤回此前“重复语言 key 导致启动失败”的决定：翻译属于允许降级的文本能力，多物料协作中的文案问题应允许运行后检查修复。此修正优先于此前认可，不能在实现或验收中恢复为致命安装错误。

已确认行为边界：

- 应用显式文案覆盖仍优先；物料文案缺失、同语言同完整 key 重复或局部无效文本不能阻止实例创建、编辑、预览或打印。
- 相同 key、相同文本允许共享，不因多来源重复报错。相同 key、不同文本需要确定的选值与可追踪诊断，继续运行。
- 通用文案集中维护，由框架内部装配，不要求使用者补装 locale 插件；集中维护是维护方向，不是阻止多物料协作的启动门禁。
- 重复物料/插件身份仍按先前规则处理；翻译 key 与物料身份不是同一种冲突。不得把文案警告升级为整个物料安装失败。

为落实上述边界，采用以下选值与诊断方案，不声称用户逐项确认过具体排序细节：

1. 保持宿主非空字符串优先；其余按创建配置中集合展开后的声明顺序，选择首个有效非空文本，不使用异步完成顺序。语言数据按声明来源保存，不改变插件实际初始化顺序。
2. 同 key 同文本不警告；同 key 不同文本保留首个有效值，记录非阻断诊断，含语言、完整 key、来源及实际采用来源。应用显式覆盖不算冲突。
3. 空值/可隔离的非字符串叶子视为未命中，继续查找其他来源；缺少可用文本时返回 key。不同文本和无效叶子的诊断按实例、语言、key、来源去重，不随每次渲染刷屏。缺失 key 可通过诊断检查，不强制弹窗或逐帧警告。
4. 保留现有整棵语言树选择：存在 locales[code] 时查该树，否则查 messages；单个 key 缺失不会回到同一来源的 messages，而是继续下一来源。此次只修改错误分级，不顺带改变已有语言 fallback 语义。
5. 切换语言时用相同顺序重新选择；覆盖和诊断不写回物料声明。启动失败/销毁按 owner 释放本实例词条索引及订阅，不修改共享只读声明。

源码依据：当前 Designer 先查宿主，再按登记顺序取首个非空字符串；物料词条已有命名空间，共享表格词条已有公共来源。多来源翻译冲突的验证应证明“选择稳定、来源可查、实例继续运行”，不能要求创建拒绝。

### 已确认：资源范围与销毁结果

采用两项相互配套的规则：

1. 声明对象可以跨 Host 只读复用；运行实例、订阅、factory 缓存、Node 编辑会话、Render Session 和输出挂载均归属于明确的 Host 或其子范围。销毁按“先失效，再停用消费者，再释放短范围输出/会话，最后释放 Host 能力”的顺序执行。这样一个 Viewer 的图表实例、DOM 监听器或 locale 订阅不会泄漏到另一个 Viewer。
2. `destroy()` 始终完成清理流程并返回结构化结果；结果包含清理错误列表，而不是遇到第一项错误就拒绝并中断。创建失败时，启动首因继续作为创建错误返回，回滚产生的清理错误附加在错误信息中。调用方可以等待完成并决定是否记录清理问题，不需要为了继续释放资源再捕获一次异常。

确认来源：用户在纠正文案错误分级的同一轮明确回复“这一轮两项都接受”。具体资源类型和 Render Session 的子范围由后续票据细化；此处确定所有权方向、失效顺序和“清理继续、结果汇总”的外部语义。

### 所有权、迟到与清理的代码落实

安装 Scope 拥有贡献、服务订阅及 Host 级 factory 缓存；Node 编辑会话、Render Session 和输出挂载拥有更短的子范围，具体层次见[Render Session 决议](./08-render-session.md)。声明对象跨 Host 只读复用，任何可变实例和缓存不得跨 Host 共享。

公开 `destroy(): Promise<DisposeResult>`：调用时在第一个 await 之前进入 disposing、递增 generation、拒绝新工作，立即使所有迟到任务失效；随后停止编辑/UI/渲染消费者、清理输出及临时会话、逆安装顺序释放 Scope，Scope 内逆登记顺序清理。一次异常不能中断剩余清理。完成后 disposed，错误以 owner/phase/cause 聚合返回。重复 destroy 返回同一完成 Promise；创建失败用同一清理机制并随创建错误交付结果。

受控 lazy/font/data 等任务同时捕获 Host、Scope 和 task generation；完成和失败都检查有效性。失效结果不得回写缓存、DOM、页数或活动诊断。产生可关闭资源的迟到结果必须自清理，关闭失败进入独立清理结果，不冒充当前渲染诊断。无法取消的外部 Promise 不强行阻塞 destroy；必须已撤销订阅和发布能力，并安装最终释放处理器。可等待的已取得资源在 destroy 完成前释放。

setup 只登记声明和受管清理，不直接网络写入、改全局对象或创建无 owner 资源。框架保证范围是受控上下文和资源管理器登记的资源，不声称能回滚任意外部副作用。首版不承诺热替换、单插件卸载、HMR 或自动依赖重启；需要换集合则 await destroy 后新建 Host。

### 实施验收

实施时公共行为测试覆盖上表、最终组合校验、locale 冲突非阻断、稳定选值与宿主覆盖恢复、两 Host 隔离、清理错误继续执行、重复 destroy、lazy 迟到自清理。已确认的门禁是：创建失败不交付部分可用实例，失败实例的受管资源被清理；销毁停止新工作与旧任务写回，清理错误不阻止其他清理。不再测试或实现可选插件失败跳过模式。

## 决策历史

2026-10-10 取代原“同一 Scope 第一次 owner 保持有效”的矛盾验收，保留既有其他 owner 与回滚当前事务分别定义。取消旧 API 转发和同步 destroy 兼容要求；原原则中的资源所有权与首版生命周期范围继续有效。

最终修正：翻译问题从致命启动冲突改为可恢复文本诊断；资源范围与销毁结果获确认；首版无公开插件依赖或安装排序配置。各轮确认来源已在相应小节记录，本票关闭。
